# Stage 9 API performance measurements

Stage 9 makes slow server requests easier to investigate before attempting a
200-user capacity test. It adds response timings to 15 API operations, optional
sampled server logs and an offline log summary. It does not make a capacity
claim, change gameplay, add polling, or access hosted data during implementation.
No SQL migration, new dependency, commit, push or deployment is included.

## What is measured

Each instrumented response adds a small `Server-Timing` header. Browser developer
tools can display these measurements; the header format is documented by
[MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Server-Timing).
The metric names are fixed, not constructed from user input.

| Metric | Meaning |
| --- | --- |
| `app` | Time inside the instrumented handler, through response construction |
| `auth` | The explicit user verification call in practice or dashboard |
| `data` | The practice RPC or dashboard snapshot operation, including its processing |
| `service` | Multiplayer service work, including any auth and database work inside it |

Coverage includes dashboard reads; practice attempt creation and result saving;
Trainer question delivery; the public multiplayer directory; lobby reads,
presence and leave; round reads and answers; readiness and delivery acknowledgments;
spectator reads and leave; and result acknowledgments. There are 15 operation
labels across 11 route files. The logged method is the configured handler method;
a framework-generated HEAD response that calls GET shares that GET label.

The handler total does not include cold-start/module initialization, the shared
authentication proxy, network transfer, CDN queues, browser rendering or response
body delivery. Multiplayer `service` is not pure database execution time. Direct
browser-to-Supabase calls, including Question Bank snapshots, bookmarks and
Trainer session saves, do not pass through these Next.js handlers. Server page
renders, Challenge, account/admin endpoints and paid tutor requests are outside
this stage. Use browser and provider measurements for those paths.

Ordinary responses also receive a fresh `X-Mao-Request-Id`. It is generated by
the server for that execution, not accepted from an incoming header and not tied
to an account. The public-directory endpoint deliberately omits this header:
its successful responses can be shared by the CDN. A cached `Server-Timing`
value describes the original server execution, not a new measurement for each
viewer. Existing cache headers and cookies are unchanged. No cross-origin timing
permission is added.

## Logging controls and privacy

Timing headers work without enabling logs. The new custom logs are off by
default. Set the server-only environment variable `MAO_API_METRICS=1` to enable
them on a deployment; never use a `NEXT_PUBLIC_` prefix.

When enabled, the observer selects all returned HTTP statuses of 400 or higher,
all completed handlers taking at least 1,000 ms, all uncaught exceptions, and
approximately one percent of other completed handlers. Output is capped at
60 records per sixty-second window per observer instance/server process. This
is not a global site-wide limit: autoscaling can create multiple processes.
After the cap, eligible records are dropped; the next emitted record reports
the number suppressed by that process since its last log. Shutdown can lose
that notice, so it is not a complete traffic count.

The JSON records contain only a fixed operation label, configured method,
generated request ID, response status, durations, phase counts, sampling reason
and suppression count. They do not include URLs, query strings, room/account
IDs, IP addresses, cookies, headers, answers, request/response bodies, tokens,
or raw exception messages/stacks. Existing platform access logs and other
application logging are not changed by this stage.

A caught application error keeps its existing response and status. An uncaught
exception is rethrown unchanged and logged with a null status because the
framework has not yet chosen the final HTTP response. Such a response cannot
be assigned a correlation header by this observer. If an operation outlives a
handler deadline, its phase is marked `pending` and its timing header says
`incomplete`; a later completion cannot log again or change the earlier record.

The observer does not retry requests, create database records, call a telemetry
service, or read request bodies. Logging/sampling failures do not replace the
application's response or original exception. It returns the original Response
object without consuming its body; immutable response headers are left alone.
The few fixed spans use bounded memory. Existing authorization, mutation checks,
answer identities, response bodies and cache decisions remain in their routes.

## Investigating a slow request

1. Open browser developer tools, choose Network, and reproduce the issue once.
   Select the relevant API request. Record its status and total browser duration.
2. Inspect `Server-Timing` and, except on the public directory, `X-Mao-Request-Id`
   in Response Headers. Do not share request cookies, authorization headers,
   full URLs with private query parameters, or an unredacted HAR export.
3. A large `auth` measurement points to user verification time; a large `data`
   measurement points to the snapshot/RPC operation; a large multiplayer
   `service` measurement needs further provider/query investigation. These are
   observations, not proof of a particular database fault.
4. If the browser's total is large but `app` is small, investigate unmeasured
   time such as the proxy, cold start, connection, transfer or client work.
   Compare the same action across devices and networks before attributing it.
5. If custom logs are enabled, search the deployment's runtime logs for
   `mao_api_metric` and the generated request ID. A missing record can mean
   sampling, suppression, disabled logging or process termination; it does not
   prove the request never ran. Responses produced before reaching the handler
   may have no timing or correlation headers.

No continuous browser telemetry collector is added. The original Question Bank
warning still needs its failed direct Supabase request or safe `QB-...` reference
code; these API timings alone cannot diagnose that separate read.

## Offline summaries

Export a bounded set of metric messages as JSONL, one JSON object per line. The
summary accepts raw metric objects or export objects whose `message` field holds
the JSON metric. Other log formats are ignored and counted; zero accepted records
means the export format or logging configuration needs checking, not zero errors.

```sh
cd "/path/to/mao-practice" &&
npm run --silent metrics:summary < /absolute/path/to/metric-messages.jsonl
```

Replace the example path with your actual export. This command only reads local
input and prints a summary. It makes no network calls and does not upload logs.
It omits request IDs and unrelated message contents from the report. Limits of
16 MiB input, 16,384 characters per line, 100,000 lines and 50,000 accepted records
bound processing; exceeding a limit stops with an error rather than printing a
partial report as complete.

Results are grouped by operation and selection reason. Percentiles describe
only the records in that logged group. Slow/error logs are deliberately selected
more often than fast successes, and the output cap drops more records during
bursts. Do not combine these groups into whole-traffic percentiles, throughput,
error rates or capacity evidence. Suppression notices concern an entire server
process and cannot be attributed to the operation on the reporting record.

## Local verification

All 368 unit/regression tests, lint, TypeScript and the production Webpack build
passed. Tests exercise all 15 operation labels and verify fixed-label privacy,
fresh IDs, original Response identity, cookies, cache/retry headers, empty 204
responses, unchanged request validation and origin checks, exact exception
propagation, unfinished phases and offline report bounds. A 200-call in-process
failure burst produces at most 60 custom log lines in its window. That checks
the log cap, not a database, network or real-user capacity limit.

The production-browser test runs real Next.js handlers locally. It verifies
seven error responses correlate to their custom log records, input canaries do
not appear in those records, guest Trainer content still matches the catalog,
and the stubbed public directory retains its cache policy. A test-only preload
blocks external server fetches, including build-time-inlined provider URLs, and
the browser blocks external requests. No real account or hosted database is used.

The existing production Question Bank navigation and guest Trainer regressions
also pass. Lobby leave/recovery, public-directory coalescing and multiplayer
client regressions are included in the final check. No UI or question-content
files are changed. The measured Question Bank entry bundles match Stage 8 exactly:
77,278 compressed bytes per division listing and 168,906 for an individual question.
Instrumentation is server-only; the offline summary script is not shipped to browsers.

```sh
npm run test:tutor-safety
npm run lint
npx tsc --noEmit --incremental false
npm run build -- --webpack
node scripts/measureQuestionBankBundles.mjs
node --experimental-strip-types tests/stageNine.next.browser.mjs
node --experimental-strip-types tests/stageThree.next.browser.mjs
node --experimental-strip-types tests/stageFour.next.browser.mjs
node tests/stageOne.browser.mjs
node tests/multiplayerClient.browser.mjs
git diff --check
```

The browser checks require local Chromium and an already-built application.
They are not instructions to run a load test against the hosted site.

## Rollout and rollback

1. Review only Stage 9 route, observer, test, summary-script, package-script and
   documentation changes. Leave unrelated account-deletion/security files
   unstaged. There is no migration 055 and no Supabase SQL to execute.
2. Deploy the matching application through the existing Git/Vercel workflow.
   Timing headers are available with custom logging still disabled.
3. Check an ordinary Trainer question request and a signed-in practice answer,
   dashboard read and lobby visit. Confirm the original actions work and timing
   headers are present. Check the public directory still has its public cache
   header and does not gain a request-ID header or account cookie.
4. For an initial diagnostic window, optionally set `MAO_API_METRICS` to `1` in
   the desired Vercel environment and redeploy. Start with Preview. Enable it in
   Production only if you want the custom runtime records there. Check the
   current platform log retention and allowance before leaving it enabled.
5. Use an existing failed request or one invalid read on Preview to confirm a
   log record and response ID agree. Avoid repeatedly causing errors or spending
   tutor quota merely to generate logs. Summarize an export locally if useful.
6. Remove the variable or set it to `0`, then redeploy to stop custom logging.
   Timing headers remain. To remove the instrumentation too, roll back the
   application deployment; no database restore or data deletion is required.

No environment or hosting settings were changed during implementation. The
observer adds small local CPU/header overhead, not a demonstrated speedup.
Optional logs consume the hosting platform's normal logging resources; sampling
and the per-process cap are not a promise of zero cost.

## Before a hosted 200 user test

The next capacity-validation stage needs separate approval for the target
environment, synthetic accounts/rooms, duration, traffic mix, request/spending
budget, stop criteria and cleanup. Use a staging application with a staging
database, not a preview connected to production user data. Do not use the older
Realtime-only script as proof of complete website capacity: broadcast delivery
does not exercise page loading, authentication, gameplay writes or saved data.

A proposed progression is 25, 50, 100 and then 200 active synthetic users, with
several minutes of steady traffic at each level and review between levels.
An illustrative 200-user mix is 100 practicing, 50 in lobbies, 40 in matches and
10 spectating; this is a proposed workload, not measured school usage. Also test
a separately approved lobby-heavy scenario. Two hundred lobby clients alone
average about 40 presence requests per second at the existing five-second
heartbeat interval, before other reads, auth and game actions.

Keep paid tutor calls out of that first test and validate tutor capacity
separately under its existing limits. Measure attempted/completed operations,
unexpected errors, timeouts, end-to-end p50/p95 latency, CDN cache behavior,
database connections/CPU and Realtime delivery. Verify no duplicate saves,
cross-account results, over-capacity joins or stale-tab interference. Target
roughly one to three seconds for other viewers to see an accepted lobby leave
under normal networking, as specified in Stage 2; crashes still use the longer
presence lease and recovery path. Agree on other latency/error thresholds before
testing rather than declaring success from these sampled handler logs afterward.

No hosted load generator was run or new live load-test command added in this
stage. A successful local build and these observations are not certification
that the deployed site supports 200 concurrent users.
